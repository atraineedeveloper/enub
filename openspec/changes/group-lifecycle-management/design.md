# Design

## Data and integrity
Add updated_at, archived_at, archived_by and positive version (initial 1); existing records remain active. Preflight identity nulls, trimmed/upper-case letter collisions, FK integrity and exact migration history. Enforce non-null and canonical group identity only after verifying legacy compatibility. Preserve unique identity across archived and active groups. Confirm institutional allowed letter and year conventions before choosing restrictive ranges; reject blank letters. Keep existing schedule FK with NO ACTION/RESTRICT, never CASCADE. Audit table in non-exposed schema with actor UUID, group ID independent of FK to groups, action, time, before/after snapshots and bounded reason; client cannot write/alter events. Avoid collecting PII beyond actor identifier. Decide retention with institution; no automatic purge.

## Authorization and transaction model
Existing app role from trusted profiles, not editable user metadata. Authenticated reads unchanged; staff/admin create, edit, archive, reactivate; admin only hard delete and audit read. Unassigned authenticated users retain existing catalog read only. Prefer invoker and RLS; if privileged internal trigger/helper is essential, use non-exposed schema, restricted grants, empty search_path, fully qualified names and explicit actor checks. Never expose service key. Enforce rules on all mutation paths, including existing direct inserts/updates, not only UI or RPC. Audit and business mutation must commit or roll back together. Do not grant client direct audit writes. Version check on updates/deletes; stale version returns stable conflict. Use server-side version increment and timestamps. Do not accept client-provided owner, version increments, timestamps or audit fields.

## Race conditions and historical invariants
Lock the group row in lifecycle mutation, and use compatible row-lock protocol for schedule assignment inserts or group changes. Schedule writes must lock/read target group before accepting it; serialize with archival and identity changes. Avoid deadlock by deterministic locking order when multiple groups touched. Verify actual transaction semantics in two-session concurrency tests, not merely pgTAP single-session tests. Retain FK as final deletion protection. Do not prevent legitimate edits to existing historical assignments solely because group archived; block new assignments or reassignment into archived groups. Block identity changes if any assignment references group; no deletion of related rows. Return clear stable error codes for dependencies, stale version, duplicate, invalid fields, forbidden, missing record. Define reason for archive/reactivate/delete; preserve history.

## UI and query behavior
Use existing menu/modal/form patterns, role-aware actions, accessible confirmation, explicit archived filter, status and reason; disable duplicate submissions, refresh groups/schedule queries on success, refresh on conflict. Keep archived groups available to historical schedule joins and PDF regeneration; filter only selection for new assignments and appropriate current views, never global historical query. Reuse existing create form conventions. Handle ambiguous transport outcomes without blind retry. No optimistic destructive UI updates.

## Deployment
Use CLI-generated migration name; fresh isolated Supabase database, SQL lint, pgTAP, TypeScript/lint/unit/build plus concurrency and regression tests. Confirm backup is decryptable and restoration rehearsed in isolated environment; never restore into production. Preview must not mutate production. Apply additive migration before compatible frontend, verify remote metadata/permissions and row counts, then merge/deploy after approval; rollback frontend first, do not blindly revert schema or delete audit history. No paid resources without approval.
