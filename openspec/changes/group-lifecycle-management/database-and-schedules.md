# Detailed database and schedule integration design

## Verified baseline
Production read-only: 29 groups, 24 referenced, 5 unreferenced, admission years 2020–2026, letters A/B/C, zero incomplete identities, zero normalized collisions, zero noncanonical letters, zero orphan non-null group references. No application triggers on groups or schedule_assignments at inspection. FK schedule_assignments.group_id references groups.id without cascade. Existing authenticated read and staff/admin insert policies; no update/delete. Re-run all preflight checks immediately before migration. Do not infer that A/B/C are the only permissible institutional letters or that 2026 is the maximum valid year.

## Proposed schema and contracts
Add version integer not null default 1 with positive check, updated_at timestamptz not null default now(), archived_at timestamptz nullable, archived_by uuid nullable with paired nullability check. Keep original IDs, created_at and full identity uniqueness. Normalize letter with upper(btrim(letter)); enforce nonempty and canonical via server validation and check; require identity columns after preflight; don't impose unsupported year/letter ranges. Audit schema group_admin_private (not exposed), events append-only to app clients, identity bigint independent of group FK, actor uuid, action text with enumerated check, timestamp, before/after jsonb, reason length bounded (proposed 500 chars). Avoid storing names/emails. Server sets metadata, never trusts client actor. No automatic deletion/archival.

## Access strategy
Keep existing direct creation compatible with old frontend, restrict insert column grants to identity fields where feasible (verify actual grant/sequence usage and existing clients). Server trigger normalizes and audits creation, rejects unauthorized roles. New lifecycle RPCs take group id, expected version, explicit allowlisted fields and reason where relevant; authenticated only; no direct client UPDATE/DELETE grant. Prefer invoker wrapper and narrowly privileged internal implementation in non-exposed schema with explicit auth.uid() and trusted current_app_role checks, empty search_path, qualified references, revoke PUBLIC/anon execution; evaluate schema usage/execution grants so internal functions cannot be called via exposed API. No broad bypass of RLS. Read-only admin audit access via narrow authorized paginated RPC if needed. Use testable error mapping (duplicate 23505, FK 23503, forbidden 42501, and distinct custom codes for stale version, archived group, protected history and missing record). Audit failure rolls back mutation. Verify all actual grants/default grants, including service maintenance behavior.

## Lock protocol
Under normal READ COMMITTED, lifecycle functions lock target group FOR UPDATE before checking references, archive state and version. Schedule trigger BEFORE INSERT OR UPDATE OF group_id, semester_id locks NEW group FOR SHARE (conflicts with FOR UPDATE and ordinary non-key updates) when creating an assignment or changing group/semester; reject archived target. Existing edits retaining group and semester remain permitted. Ensure locking precedes dependency query and that visibility after a competing transaction commits is proven in two-session tests. Retain FK as last barrier. Group identity edits/delete block if any reference exists, even historical. Archive may coexist with existing schedules, but serialized new assignments must fail once archive commits. Test reverse race ordering, multiple target groups, deadlock retry and isolation levels; restrict supported mutation isolation or prove behavior under higher isolation. No untested concurrency guarantee. Add index on schedule_assignments(group_id) only if equivalent index absent.

## Concrete frontend paths
- apiScheduleAssignments.ts exposes direct insert, create/edit, and delete; guard in PostgreSQL covers every insert path, not just React hooks. Map stable archive rejection to Spanish message.
- useCreateScheduleAssignments and useEditScheduleAssignments call shared createEditScheduleAssignments.
- ScheduleDashboard.tsx currently shares semester-filtered currentGroups with SemesterContext and ScholarSchedule. Keep historical view candidates including archived groups (and referenced groups outside calculated grade window if needed; verify existing behavior). Do not globally filter useGroups.
- CreateEditScholarSchedule.tsx uses context for group selection and subject filtering. New selection only active; edit may retain original archived group in same semester; cannot move to archived group or create from archived empty slot. Handle stale cached group status via DB rejection.
- ShowScholarSchedule.tsx selects group and renders ScheduleGroupPDF; keep archived references visible, suppress add-from-empty-slot for archived group, preserve existing schedule/PDF reads.
- GroupTable.tsx currently filters out graduates by calculated semester <=8; provide independent academic and administrative filters plus all/history view; avoid losing future/graduate groups.
- CreateGroupForm.tsx currently submits raw form object; introduce typed validated identity payload, parse numeric strings explicitly, reject empty/unsafe integers. Keep existing create UX.
- GroupRow.tsx currently only inert Edit menu; use role-gated actions and accessible confirmation with reason; server always enforces.
- Invalidate groups and relevant schedule caches after mutations; do not optimistic-delete. Unknown outcomes require refresh.

## Acceptance gates
Fresh local migration, baseline preservation, all roles and direct bypass attempts, audit integrity and rollback, concurrency tests with separate sessions, historical display/PDF regression, frontend lint/typecheck/test/build. Verify backup restore in isolated environment before production approval. No production writes or migration from this design document.
